# 2. Business Questions และ Measures

## 2.1 Measures สำหรับวัดผลการดำเนินงาน

แบ่งเป็น 2 ระดับตามหลัก Dimensional Modeling

- **Base Measure** — เก็บจริงในคอลัมน์ของ Fact Table บวกกันได้ทุกมิติ (fully additive)
- **Derived Measure** — ไม่เก็บในตาราง แต่คำนวณตอนแสดงผลบน BI Tool
  เพราะเป็นอัตราส่วน ถ้าเก็บไว้แล้วเอาไปบวกกันจะได้ค่าผิด (non-additive)

> **เหตุผลที่ต้องแยก** — ถ้าเก็บ "ยอดขายเฉลี่ยต่อบิล" ลงใน Fact แล้วผู้ใช้ลากไปรวมทั้งเดือน
> ระบบจะเอาค่าเฉลี่ยมาบวกกัน ซึ่งไม่มีความหมายทางคณิตศาสตร์
> จึงต้องเก็บเฉพาะตัวตั้งและตัวหารแยกกัน แล้วให้ BI Tool หารตอนแสดงผล

---

### Base Measures

#### M1 — Total Revenue (ยอดขาย)

| หัวข้อ | รายละเอียด |
|--------|------------|
| **ความหมาย** | มูลค่าขายรวมก่อนหักต้นทุน หน่วยเป็น USD |
| **วิธีคำนวณ** | `SUM(quantity × unit_price)` โดย `unit_price` ดึงจาก `dim_pizza` ณ เวลาที่ขาย |
| **ระดับที่เก็บ** | คำนวณล่วงหน้าเก็บเป็นคอลัมน์ `line_revenue` ในทุกแถวของ Fact |
| **ประโยชน์** | ตัวชี้วัดหลักที่ผู้บริหารใช้ติดตามผลประกอบการ เป็นตัวตั้งของอัตราส่วนเกือบทุกตัว |
| **ค่าอ้างอิงปี 2015** | **$817,860.05** |

> เก็บ `line_revenue` ไว้เลยแทนที่จะให้ BI คูณเอง เพราะถ้าอนาคตมีการเปลี่ยนราคา
> ค่าที่บันทึกไว้จะยังสะท้อนราคา ณ วันที่ขายจริง ไม่ถูกราคาปัจจุบันเขียนทับ

#### M2 — Total Quantity Sold (จำนวนที่ขายได้)

| หัวข้อ | รายละเอียด |
|--------|------------|
| **ความหมาย** | จำนวนถาดพิซซ่าที่ขายออกไป |
| **วิธีคำนวณ** | `SUM(quantity)` |
| **ประโยชน์** | ใช้วางแผนวัตถุดิบและกำลังการผลิตในครัว ซึ่งสนใจ "กี่ถาด" ไม่ใช่ "กี่บาท" |
| **ค่าอ้างอิงปี 2015** | **49,574 ถาด** |

> ต้องดูคู่กับ M1 เสมอ เพราะเมนูราคาถูกที่ขายดีมากอาจมี "จำนวน" สูงแต่ "รายได้" ต่ำ
> การดูตัวเดียวจะนำไปสู่การตัดสินใจผิด

#### M3 — Number of Orders (จำนวนบิล)

| หัวข้อ | รายละเอียด |
|--------|------------|
| **ความหมาย** | จำนวนบิล นับเป็นตัวแทนของจำนวนครั้งที่ลูกค้าเข้ามาใช้บริการ |
| **วิธีคำนวณ** | `COUNT(DISTINCT order_id)` |
| **ประโยชน์** | ใช้วัดปริมาณงานที่หน้าร้านและครัวต้องรับ เป็นฐานในการจัดกะพนักงาน |
| **ค่าอ้างอิงปี 2015** | **21,350 บิล** |

> เป็น measure แบบ **distinct count** ต้องระวังเป็นพิเศษ เพราะหนึ่งบิลกินหลายแถวใน Fact
> (เฉลี่ย 2.28 แถวต่อบิล) การใช้ `COUNT(*)` จะได้ 48,620 ซึ่งคือจำนวนรายการ ไม่ใช่จำนวนบิล

### Derived Measures

#### M4 — Average Order Value (ยอดขายเฉลี่ยต่อบิล)

- **วิธีคำนวณ** `M1 ÷ M3`
- **ประโยชน์** วัดว่าลูกค้าหนึ่งรายจ่ายเงินเฉลี่ยเท่าไร ใช้ประเมินผลการเชียร์ขายเพิ่ม
  (upselling) เช่น ถ้าออกโปรฯ ขายพ่วงแล้วตัวเลขนี้ไม่ขยับ แปลว่าโปรฯ ไม่ได้ผล
- **ค่าอ้างอิงปี 2015** **$38.31 ต่อบิล**

#### M5 — Items per Order (จำนวนชิ้นเฉลี่ยต่อบิล)

- **วิธีคำนวณ** `M2 ÷ M3`
- **ประโยชน์** บอกขนาดของกลุ่มลูกค้า ค่าสูงแปลว่าเป็นกลุ่มครอบครัวหรือสั่งเข้าออฟฟิศ
  ซึ่งใช้เวลาทำนานกว่า มีผลต่อการจัดคนในครัว
- **ค่าอ้างอิงปี 2015** **2.32 ถาดต่อบิล**

#### M6 — Revenue per Trading Day (ยอดขายเฉลี่ยต่อวันทำการ)

- **วิธีคำนวณ** `M1 ÷ COUNT(DISTINCT วันที่มีการขาย)`
- **ประโยชน์** ใช้เทียบผลงานระหว่างเดือนได้อย่างเป็นธรรม เพราะแต่ละเดือนมีวันทำการไม่เท่ากัน
  การเทียบยอดรวมดิบๆ จะทำให้เดือนที่ร้านปิดหลายวันดูแย่เกินจริง
- **ค่าอ้างอิงปี 2015** **$2,284.53 ต่อวัน** (จาก 358 วันทำการ)

#### M7 — Gross Profit และ Margin % (กำไรขั้นต้น) *— รอตารางต้นทุน*

- **วิธีคำนวณ** `M1 − SUM(quantity × unit_cost)` และ `Gross Profit ÷ M1 × 100`
- **ประโยชน์** เมนูที่ขายดีที่สุดไม่จำเป็นต้องทำกำไรดีที่สุด measure นี้คือตัวเดียว
  ที่ตอบได้ว่าควรดันเมนูไหน
- **สถานะ** ข้อมูลต้นทางไม่มีต้นทุน ต้องจัดทำตาราง `ingredient_cost` ประกอบขึ้น
  และ**ระบุในรายงานว่าเป็นข้อมูลสมมติ**

### BQ2 — ขนาดพิซซ่าใดเป็นตัวทำรายได้หลัก และขนาด XL/XXL คุ้มที่จะเก็บไว้หรือไม่?

| | |
|---|---|
| **ผู้ถาม** | ฝ่ายจัดซื้อ / หัวหน้าครัว |
| **Measure** | M1, M2 |
| **Dimension** | `dim_pizza` (size) |
| **กราฟ** | โดนัทหรือแท่งซ้อน แสดงสัดส่วนรายได้ตามขนาด |

**สิ่งที่ข้อมูลบอกแล้ว** — ขนาด L ครอง **45.9%** ของรายได้ ขณะที่ XL ได้ 1.7%
และ XXL ได้เพียง **0.1% (28 ถาดทั้งปี)**

> ⚠️ **กับดักที่ต้องระวัง** — ตัวเลข XXL ต่ำ **ไม่ได้แปลว่าลูกค้าไม่ชอบขนาดใหญ่**
> เพราะเมื่อตรวจตาราง `pizzas` พบว่า XL และ XXL **มีขายแค่เมนูเดียวคือ The Greek Pizza**
> จาก 32 เมนู การสรุปว่า "ควรเลิกขายไซซ์ใหญ่" จึงเป็นข้อสรุปที่ผิด
> ข้อเสนอแนะที่ถูกต้องคือ *"ทดลองเปิดขายขนาด XL กับเมนูขายดีอันดับต้นๆ
> เพื่อพิสูจน์ว่าอุปสงค์มีจริงหรือไม่"*
>
> ประเด็นนี้ใช้เป็นตัวอย่างในหัวข้อ **การตรวจสอบผลลัพธ์จาก AI** ได้โดยตรง

### BQ8 — เหตุใดร้านจึงปิดทำการ 7 วันในปี 2015 และกระทบรายได้เท่าไร?

| | |
|---|---|
| **ผู้ถาม** | เจ้าของร้าน |
| **Measure** | M6 (ใช้ประมาณรายได้ที่เสียไป) |
| **Dimension** | `dim_date` (full calendar) |
| **กราฟ** | ปฏิทิน Heatmap ทั้งปี แสดงช่องว่างให้เห็นชัด |

**สิ่งที่ข้อมูลบอกแล้ว** — ร้านเปิดขายจริง 358 จาก 365 วัน วันที่ปิดคือ

| วันที่ | วัน | หมายเหตุ |
|--------|-----|----------|
| 24–25 ก.ย. | พฤหัส–ศุกร์ | ไม่ตรงวันหยุดใด |
| 5, 12, 19, 26 ต.ค. | **วันจันทร์ทั้ง 4 สัปดาห์** | เป็นวันจันทร์ทุกวันของเดือนตุลาคม |
| 25 ธ.ค. | ศุกร์ | วันคริสต์มาส |

> การพบว่าร้านปิด**ทุกวันจันทร์ตลอดเดือนตุลาคม** เป็นรูปแบบที่เกิดขึ้นเองไม่ได้
> มีสองความเป็นไปได้คือร้านหยุดตามนโยบายชั่วคราว หรือ**ข้อมูลเดือนนั้นสูญหาย**
> ต้องระบุเป็นข้อจำกัดของข้อมูลในรายงาน และเป็นเหตุผลว่าทำไมต้องใช้ M6 แทนยอดรวมดิบ
>
> คำถามนี้แสดงให้เห็นว่ากลุ่มไม่ได้แค่สร้างกราฟ แต่**ตรวจสอบความสมบูรณ์ของข้อมูล**ด้วย

## 2.4 ตัวเลขควบคุมสำหรับตรวจสอบหลัง Load

ใช้ยืนยันว่าข้อมูลที่ผ่าน ETL เข้าคลังแล้วไม่ตกหล่นหรือถูกนับซ้ำ
ค่าเหล่านี้คำนวณจากไฟล์ต้นทางโดยตรง **หลังโหลดเข้า DW ต้องได้ตัวเลขเดิมทุกตัว**
