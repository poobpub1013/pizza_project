# 1. บริบทและวัตถุประสงค์ของโครงการ

## 1.1 ปัญหาทางธุรกิจ (Business Problem)

ร้านพิซซ่าแห่งนี้เปิดขายมาตลอดปี 2015 มีรายการขายสะสมในระบบ POS จำนวน
**21,350 ออเดอร์** คิดเป็น **48,620 รายการสินค้า** จากเมนู **32 ชนิด** ที่แตกออกเป็น
**96 SKU** (4 หมวด × 5 ขนาด) แต่ข้อมูลทั้งหมดนี้ถูกใช้เพียงเพื่อ**ปิดยอดขายรายวัน**เท่านั้น
ไม่เคยถูกนำมาวิเคราะห์เพื่อการตัดสินใจ

ผลที่ตามมาคือการบริหารร้านยังอาศัย "ความรู้สึก" ของผู้จัดการเป็นหลัก และเกิดปัญหา 4 ด้าน

**1. ไม่รู้ว่าเมนูไหนควรอยู่หรือควรไป**
เมนู 96 SKU สร้างภาระทั้งด้านการจัดเก็บวัตถุดิบและความเร็วในการผลิต
แต่ร้านไม่มีข้อมูลว่ารายการใดขายไม่ออกจนควรตัดทิ้ง หรือรายการใดที่ขนาดบางขนาดแทบไม่มีคนสั่ง

**2. จัดกะพนักงานไม่ตรงกับความต้องการจริง**
ระบบบันทึกเวลาสั่งซื้อละเอียดถึงระดับวินาที แต่ไม่เคยถูกนำมาหาว่าชั่วโมงใดคือชั่วโมงเร่งด่วนจริง
ทำให้บางช่วงคนล้นงาน บางช่วงลูกค้ารอนาน

**3. วางแผนวัตถุดิบด้วยการคาดเดา**
สั่งของตามความเคยชิน เกิดทั้งของเสียจากการสั่งเกิน และการเสียโอกาสขายจากของขาด

**4. อธิบายยอดขายที่ผันผวนไม่ได้**
ยอดขายรายวันขึ้นลงชัดเจน แต่ร้านไม่สามารถแยกได้ว่าเกิดจาก**ปัจจัยภายใน**
(เมนู ราคา โปรโมชัน) หรือ**ปัจจัยภายนอก** (สภาพอากาศ วันหยุด ฤดูกาล)
เมื่ออธิบายสาเหตุไม่ได้ ก็พยากรณ์ล่วงหน้าไม่ได้ และวางแผนไม่ได้

> **ช่องว่างสำคัญ** — ข้อมูล POS เพียงลำพังตอบได้แค่ว่า *"ขายอะไรไปเท่าไร"*
> แต่ตอบไม่ได้ว่า *"ทำไม"* โครงการนี้จึงต้องนำข้อมูลภายนอกเข้ามาเชื่อมโยงด้วย

## 1.2 ผู้ใช้งานข้อมูล (Stakeholders)

| ผู้ใช้งาน | ต้องการรู้อะไร | เอาไปตัดสินใจอะไร |
|-----------|----------------|-------------------|
| **เจ้าของร้าน / ผู้จัดการ** | ภาพรวมยอดขาย แนวโน้มรายเดือน เมนูทำเงิน | ปรับกลยุทธ์ ตั้งเป้ายอด ตัดสินใจลงทุน |
| **หัวหน้าครัว / ฝ่ายจัดซื้อ** | ปริมาณขายแยกตามเมนูและขนาด รูปแบบตามฤดูกาล | วางแผนสั่งวัตถุดิบ ลดของเสีย |
| **หัวหน้ากะ** | ชั่วโมงและวันที่มีออเดอร์หนาแน่น | จัดตารางเวร กระจายกำลังคน |
| **ฝ่ายการตลาด** | ช่วงเวลาที่ยอดตก เมนูที่ขายไม่ออก ผลของวันหยุด | ออกโปรโมชัน เลือกจังหวะจัดแคมเปญ |

## 1.3 วัตถุประสงค์ของโครงการ

### วัตถุประสงค์หลัก

**พัฒนา Mini Data Warehouse และ Interactive Dashboard ที่รวมข้อมูลยอดขายจากระบบ POS
เข้ากับข้อมูลสภาพอากาศและปฏิทินวันหยุด เพื่อเปลี่ยนข้อมูลดิบที่ถูกทิ้งไว้เฉยๆ
ให้กลายเป็นเครื่องมือสนับสนุนการตัดสินใจด้านเมนู กำลังคน และการวางแผนวัตถุดิบ
ที่ผู้บริหารร้านใช้งานได้เองโดยไม่ต้องพึ่งฝ่ายไอที**

### วัตถุประสงค์เฉพาะ

**ว.1 รวมข้อมูลจากหลายแหล่งที่มีโครงสร้างต่างกันให้เป็นชุดเดียว**
นำข้อมูล 3 แหล่งมาเชื่อมกัน ได้แก่ ยอดขาย POS (CSV เชิงสัมพันธ์ 4 ตาราง),
สภาพอากาศรายชั่วโมงจาก Open-Meteo API (Nested JSON 8,760 ชั่วโมง) และ
ปฏิทินวันหยุดจาก Nager.Date API (Nested JSON)

**ว.2 ตรวจสอบและแก้ไขปัญหาคุณภาพข้อมูลอย่างเป็นระบบ**
ระบุปัญหาที่พบในข้อมูลต้นทาง แก้ไขด้วยกระบวนการที่เขียนเป็นโค้ด
พร้อมบันทึกหลักฐานก่อนและหลังการแก้ไขเป็นตัวเลขที่ตรวจสอบย้อนกลับได้
โดยไม่มีการแก้ไขไฟล์ด้วยมือในขั้นตอนใดเลย

**ว.3 ออกแบบ Data Warehouse ด้วย Dimensional Modeling**
สร้าง Star Schema ที่มี Fact Table ระดับรายการสินค้าในบิล พร้อม Dimension
ที่ครอบคลุมมิติเวลา สินค้า และสภาพแวดล้อมภายนอก โดยนิยาม Grain,
Primary Key และ Foreign Key ให้ชัดเจน

**ว.4 พัฒนากระบวนการ ETL ที่รันซ้ำได้อัตโนมัติ**
สร้าง pipeline ตั้งแต่ Extract จนถึง Load ที่สั่งรันใหม่เมื่อใดก็ได้แล้วได้ผลลัพธ์เดิม
พร้อมการตรวจสอบความถูกต้องทั้งก่อนและหลังโหลดข้อมูลเข้าคลัง

**ว.5 สร้าง Dashboard เชิงโต้ตอบที่ตอบคำถามทางธุรกิจได้จริง**
นำเสนอ Measure สำคัญพร้อมกราฟที่ผู้ใช้กรองและเจาะลึกได้เอง
โดยทุกกราฟต้องผูกกับคำถามทางธุรกิจที่ตั้งไว้ ไม่ใช่กราฟที่สร้างขึ้นเพราะทำได้

**ว.6 สรุปข้อค้นพบเป็นข้อเสนอแนะที่นำไปปฏิบัติได้**
แปลงผลการวิเคราะห์เป็นคำแนะนำที่ระบุได้ว่าใครควรทำอะไร
และคาดว่าจะเกิดผลอย่างไร ไม่หยุดอยู่แค่การบรรยายว่าข้อมูลมีหน้าตาอย่างไร

## 1.4 ขอบเขตของโครงการ (Scope)

**อยู่ในขอบเขต**
- ยอดขายทั้งหมดของปี 2015 (1 ม.ค. – 31 ธ.ค.) จำนวน 21,350 ออเดอร์
- การวิเคราะห์ระดับรายการสินค้าในบิล เมนู หมวดหมู่ ขนาด และช่วงเวลา
- ความสัมพันธ์ระหว่างยอดขายกับสภาพอากาศรายชั่วโมงและวันหยุด

**อยู่นอกขอบเขต พร้อมเหตุผล**
- **การวิเคราะห์รายลูกค้า** — ระบบ POS ต้นทางไม่บันทึกรหัสลูกค้า จึงวิเคราะห์
  การกลับมาซื้อซ้ำหรือแบ่งกลุ่มลูกค้าไม่ได้
- **การเปรียบเทียบระหว่างสาขา** — ข้อมูลมาจากร้านสาขาเดียว
- **การพยากรณ์ด้วยแบบจำลอง** — โครงการนี้เตรียม Analytical Dataset ไว้ให้พร้อม
  ต่อยอด แต่ยังไม่สร้างตัวแบบพยากรณ์

**ข้อจำกัดที่ต้องระบุ**
- ข้อมูลต้นทางไม่มี**ต้นทุนวัตถุดิบ** จึงคำนวณกำไรจากข้อมูลจริงไม่ได้
  โครงการจึงจัดทำตารางต้นทุนประกอบขึ้นเพื่อประมาณอัตรากำไร
  และระบุไว้ชัดเจนว่าเป็นข้อมูลสมมติ
- ข้อมูลต้นทางไม่ระบุที่ตั้งร้าน โครงการกำหนดให้ร้านตั้งอยู่ที่**ชิคาโก**
  เพื่อให้ดึงข้อมูลสภาพอากาศได้ ผลการวิเคราะห์ด้านอากาศจึงอยู่บนสมมติฐานนี้
