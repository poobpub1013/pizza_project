# ปัญหาคุณภาพข้อมูลที่ตรวจพบ

ทุกข้อด้านล่างเป็นปัญหา **ที่มีอยู่จริงในข้อมูลต้นทาง** ไม่ได้สร้างขึ้นเอง
ตรวจพบจากการ profile ข้อมูลหลังดึงเสร็จ

### 1. โครงสร้างแบบ Columnar ไม่ใช่ Row (Open-Meteo)

API ไม่ได้คืน array ของ record แต่คืน **array คู่ขนาน** — ต้อง transpose ก่อนใช้

```json
"hourly": {
  "time":           ["2015-01-01T00:00", "2015-01-01T01:00", ...],
  "temperature_2m": [-3.2, -3.5, ...],
  "precipitation":  [0.0, 0.1, ...]
}
```

แปลว่าจะโหลดเข้า DW ตรงๆ ไม่ได้ ต้องเขียนโค้ดแปลง 8,760 ชั่วโมงเป็นแถว

### 2. หน่วยวัดไม่ตรงกัน

API คืนค่าเป็นระบบเมตริก แต่ธุรกิจเป็นร้านในสหรัฐฯ (ราคาเป็น USD)
ผู้ใช้งานคิดเป็นหน่วยอังกฤษ → ต้องแปลงในขั้น Transform

| ตัวแปร | หน่วยที่ได้ | หน่วยที่ธุรกิจใช้ |
|--------|-------------|-------------------|
| temperature_2m | °C | °F |
| precipitation, rain | mm | inch |
| snowfall | **cm** (คนละหน่วยกับฝน) | inch |
| wind_speed_10m | km/h | mph |

### 3. รูปแบบวันที่ไม่ตรงกัน — 3 แบบจาก 3 แหล่ง

| แหล่ง | รูปแบบ | ตัวอย่าง |
|-------|--------|----------|
| orders.csv | แยกเป็น 2 คอลัมน์ | `date=2015-01-01`, `time=11:38:36` |
| Open-Meteo | ISO 8601 มีตัว `T` คั่น | `2015-01-01T00:00` |
| Nager.Date | date อย่างเดียว | `2015-01-01` |

### 4. ข้อมูลซ้ำ + Grain ไม่ตรง ทำให้ Fact Table บานปลาย

ไฟล์วันหยุดมี **16 แถว แต่มีแค่ 13 วันที่** เพราะบางวันซ้ำ

| วันที่ | ปัญหา |
|--------|-------|
| 2015-04-03 | `Good Friday` มา **2 แถว** ต่างกันแค่รายชื่อรัฐ |
| 2015-10-12 | `Columbus Day` มา **2 แถว** (`global=true` และ `global=false`) |
| 2015-10-12 | ยังมี `Indigenous Peoples' Day` ซ้อนวันเดียวกันอีก รวมเป็น 3 แถว |

**ผลกระทบที่พิสูจน์แล้ว:** join วันหยุดเข้ากับ orders แบบตรงๆ ทำให้ออเดอร์
เพิ่มจาก **21,350 → 21,414 แถว (เกินมา 64)** = ยอดขายจะถูกนับซ้ำ
ต้อง deduplicate ให้เหลือ 1 แถวต่อวันก่อน ไม่งั้น Measure ผิดทั้งกระดาน

### 5. ค่าที่เป็นรหัส อ่านเองไม่ได้

`weather_code` เป็นตัวเลข WMO 4677 — `73` แปลว่าหิมะตกปานกลาง, `95` แปลว่าพายุฝนฟ้าคะนอง
ต้อง join กับ `wmo_weather_codes.json` ถึงจะเอาไปทำ Dimension ได้

### 6. Timezone ไม่ขยับตาม DST

ขอข้อมูลด้วย `timezone=America/Chicago` แต่ API ตอบกลับมาว่า
`utc_offset_seconds = -18000` (GMT-5) **คงที่ตลอดทั้งปี**

ชิคาโกจริงๆ ใช้ CST (GMT-6) ในฤดูหนาว และ CDT (GMT-5) ช่วง DST
แปลว่าเวลาที่ API ให้มาในช่วงฤดูหนาว **เร็วกว่านาฬิกาท้องถิ่นจริง 1 ชั่วโมง**
ถ้าจะวิเคราะห์รายชั่วโมงแบบละเอียด ต้องปรับชดเชยและระบุข้อจำกัดนี้ในรายงาน

### 7. Encoding ไม่ใช่ UTF-8 (ของเดิม)

`pizza_sales/pizza_types.csv` มี byte `0x91` (smart quote แบบ Windows-1252)
ในชื่อวัตถุดิบ `'Nduja Salami` — อ่านด้วย UTF-8 แล้ว error ทันที
ต้องระบุ `encoding='latin-1'` หรือ `cp1252` ตอน extract
